## 1. 문서 위치

이 문서는 사용자, 운영자, 수집 job의 흐름을 정리하는 시나리오 기준 문서다.

```text
시나리오 문서
  -> 어떤 사용자가 어떤 화면에서 무엇을 하는지 확정
  -> 어떤 상황에서 승인/보류/제외가 필요한지 확정
  -> DB 적재/검수/snapshot 문서의 세부 기준으로 연결
```

문서별 역할:

| 문서 | 역할 |
|---|---|
| 데이터 수집 서비스 시나리오 | 사용자/어드민/수집 job이 어떤 상황에서 어떻게 동작하는지 정의 |
| 사용자 / 어드민 화면 구조 및 기능 기획 | 시나리오를 실제 화면 구조, 필터, 버튼, 상태 표시로 옮기기 위한 화면 기획 |
| 사용자 / 어드민 API 기획 | 화면 기능이 호출할 사용자/어드민 서버 API 정의 |
| 주기 수집 운영 문서 | 수집 실행, 실패 처리, 알림, snapshot 반영 기준 |
| artist_key 및 작가명 표준화 흐름 | 작가명, alias, 동명이인, 최종 artist_key 확정 기준 |
| 원천 사이트별 수집 항목 정리 | 사이트별 수집 필드와 표준화 매핑 |
| MySQL 적재 기획 | DB 테이블, job, upsert, 재실행 안전성 |

## 2. 전체 사용자 흐름

```text
[사용자]
  - 작품 정보 입력
  - 작가명 입력 또는 검색/선택
  - 예측 요청
        |
        v
[가격 예측 처리]
  - 입력값 검증
  - artist_key 확정 여부 확인
  - Warm/Cold 등 가격 예측 경로 선택
  - 예측 결과와 신뢰도/검수 필요 표시 반환
        |
        v
[사용자 화면]
  - 예측 가격 표시
  - 호당 표기는 표시용 환산값으로만 제공
  - 입력값 부족 또는 작가 미확정이면 보완 안내
```

사용자 화면의 핵심 원칙:

- 가격 예측 계산은 작품 크기 cm, 작품 메타, 작가 이력/메타를 기준으로 한다.
- 호당 가격은 계산 기준이 아니라 표시용 참고값이다.
- 사용자가 입력한 작가명이 최종 `artist_key`로 확정되지 않았으면, 운영 검수 상태에 따라 예측 신뢰도 또는 검수 필요 표시를 함께 보여준다.
- 사용자 화면에는 수집 원천 사이트명, 원천 URL, 원천 작가 ID를 노출하지 않는다. 이 정보는 어드민 검수와 운영 추적용으로만 쓴다.
- 예측 결과에는 데이터 기준일(as_of, = 참조 snapshot의 `source_cutoff_at`)을 함께 노출한다. 수집이 주 1회이므로 사용자가 보는 값은 최신 snapshot 기준이며 실제 시장 대비 최대 10일(운영 파라미터 §E `FRESH-WARN-N`) 과거일 수 있다.
- 예측 처리 결과는 `price_prediction_log`에 적재한다(`model_version`/`deployment_id`/`route` 포함). 특정 예측이 어느 모델·배포에서 나온 값인지 사후에 추적할 수 있어야 한다.

### 2.1 사용자 시나리오: 확정 작가로 예측

조건:

- 사용자가 작가명을 검색한다.
- 검색 결과에서 기존 `artist_key`가 확정된 작가를 선택한다.
- 작품 크기, 작품명, 제작연도, 재료/지지체 등 필수 입력값이 채워져 있다.

흐름:

```text
작가명 검색
  -> 확정 작가 선택
  -> 작품 정보 입력
  -> 입력값 검증 통과
  -> 가격 예측 처리
  -> 예측 가격, 신뢰도, 참고 표시값 노출
```

사용자에게 보여줄 내용:

- 선택한 작가명
- 선택한 작가의 식별 보조 정보. 예: 생년, 국적, 활동지, 대표 작품
- 입력 작품 크기 cm
- 예측 가격
- 예측 가격의 참고 범위 또는 신뢰도 표시
- 호당 환산 표시가 필요한 경우 “표시용 참고값”으로만 노출
- 1차 시장 가격 참고 카드. 예: 호당가 중앙값, 호당가 범위, 매체별 분포, 표본 수
- 데이터 기준일(as_of)/최신성 표시. 예측이 참조한 운영 snapshot의 `source_cutoff_at`를 사용자에게 그대로 보여준다.

데이터 최신성(freshness) 원칙:

- 수집은 주 1회이고 사용자 예측은 운영 중인 승인 snapshot을 참조하므로, 사용자가 보는 값은 항상 최신 snapshot 기준이며 실제 시장 대비 최대 10일 과거일 수 있다.
- 예측 응답의 `as_of`는 참조 snapshot의 `source_cutoff_at`와 같은 값이다. 화면에는 이 기준일을 “데이터 기준일”로 노출한다.
- freshness SLA: 운영 중인 snapshot의 `as_of`가 현재 시각 기준 10일을 초과하면 신선도 경고를 표시한다.

### 2.2 사용자 시나리오: 작가 검색 결과가 여러 명인 경우

조건:

- 같은 이름 또는 비슷한 이름의 작가 후보가 2명 이상이다.

흐름:

```text
작가명 검색
  -> 후보 목록 표시
  -> 사용자가 생년/국적/활동지/대표 작품을 보고 선택
  -> 선택한 후보로 예측 진행
```

사용자 화면 원칙:

- 같은 이름의 후보를 하나로 합쳐 보여주지 않는다.
- 사용자가 구분할 수 있는 정보가 부족하면 “운영 검수 필요” 상태로 안내한다.
- 사용자가 임의로 새 작가를 만들 수 있게 하지 않고, 새 작가 후보 등록 흐름으로 보낸다.

### 2.3 사용자 시나리오: 작가가 검색되지 않는 경우

조건:

- 입력한 작가명이 기존 확정 작가에 매칭되지 않는다.

흐름:

```text
작가명 검색
  -> 검색 결과 없음
  -> 신규 작가 후보 입력
  -> 작품 정보 입력
  -> 운영 검수 필요 안내
```

처리:

- 신규 작가 후보는 바로 최종 `artist_key`를 발급하지 않는다.
- 신규 작가 후보 정보는 어드민 신규 작가 후보 큐로 보낸다.
- 미확정 작가(최종 `artist_key`가 없는 작가)는 예측 시 항상 Cold 경로로 처리하고, “작가 이력 미확정 / 검수 필요” 표시를 강제로 함께 노출한다. Warm 경로(작가 가격 이력 기반)는 최종 `artist_key`가 확정된 작가에만 적용한다.

### 2.4 사용자 시나리오: 필수 입력값이 부족한 경우

조건:

- 가로 또는 세로 cm가 없다.
- 가격 예측에 필요한 작품 유형 또는 재료/지지체 입력이 없다.
- 작품이 입체/설치/영상/혼합매체 제외 후보로 판단된다.

흐름:

```text
작품 정보 입력
  -> 입력값 검증 실패
  -> 부족하거나 확인 필요한 항목 표시
  -> 사용자 수정
  -> 다시 검증
```

사용자에게 보여줄 내용:

- 수정이 필요한 필드명
- 현재 입력값
- 허용되는 입력 예시
- 예측을 진행할 수 없는 이유

### 2.5 사용자 시나리오: 예측 결과가 검수 필요로 표시되는 경우

조건:

- 작가가 확정되지 않았다.
- 작품 정보 일부가 낮은 신뢰도로 파싱되었다.
- 예측 가격 범위가 넓다.
- 수집 또는 표준화 상태가 아직 snapshot에 확정 반영되지 않았다.

흐름:

```text
예측 요청
  -> 가격 예측 처리
  -> 결과 산출
  -> 검수 필요 사유 확인
  -> 예측 가격과 검수 필요 표시를 함께 노출
```

표시 원칙:

- 검수 필요 사유를 숨기지 않는다.
- 사용자가 수정할 수 있는 문제와 운영자 확인이 필요한 문제를 분리한다.
- “가격 계산 실패”와 “계산은 되었지만 검수 필요”를 다른 상태로 보여준다.

### 2.6 사용자 시나리오: 1차 시장 가격 참고 카드 확인

조건:

- 예측 대상 작가 또는 유사 비교군에서 참고 가능한 1차 시장 작품 표본이 있다.
- 표본 수와 분포 요약을 만들 수 있다.

흐름:

```text
예측 결과 산출
  -> 참고 표본 집계
  -> 호당가 중앙값 계산
  -> 호당가 범위 계산
  -> 매체별 분포 계산
  -> 사용자 화면에 요약 카드 표시
```

사용자에게 보여줄 정보:

| 항목 | 예시 | 설명 |
|---|---|---|
| 카드 제목 | 1차 시장 가격 | 참고 시장 가격 영역 |
| 기준 라벨 | 호당가 중앙값 | 참고 표본의 대표 호당 가격 |
| 대표값 | 35만원/호 | 중앙값 기준 호당 가격 |
| 범위 | 28만 - 46만원/호 | 참고 표본의 가격 범위 |
| 매체별 분포 | 회화 33만, 드로잉 28만 | 매체별 참고 호당가 |
| 표본 수 | N=24건 | 계산에 사용한 참고 작품 수 |
| 데이터 기준일 | as_of 2026-06-25 | 카드가 참조한 snapshot의 `source_cutoff_at` |

표시 원칙:

- 원천 사이트명은 보여주지 않는다.
- 표본 개별 작품 링크나 원천 URL은 사용자에게 노출하지 않는다.
- 카드의 값은 최종 예측 가격이 아니라 사용자가 가격대를 이해하기 위한 참고 정보다.
- 카드에도 데이터 기준일(as_of, = 참조 snapshot의 `source_cutoff_at`)을 함께 표시한다. 주간 수집 특성상 카드 값은 최신 snapshot 기준이며 실제 시장 대비 최대 10일 과거일 수 있다.
- freshness SLA: 카드가 참조한 snapshot의 `as_of`가 현재 시각 기준 10일을 초과하면 신선도 경고를 함께 표시한다.

### 2.7 사용자 시나리오: 예측/데이터 장애 시 화면 폴백

조건:

- 예측 서버 또는 운영 모델(active deployment)이 응답하지 못한다.
- 또는 참조할 운영 snapshot이 없거나, snapshot의 `as_of`가 freshness SLA(10일)를 초과했다.

흐름:

```text
예측 요청
  -> 예측 처리 실패 또는 데이터 신선도 미달 감지
  -> 폴백 케이스 결정
  -> 사용자 화면에 폴백 상태 표시
```

“정상 snapshot” 정의:

- 서빙(사용자 노출/폴백) 기준의 “정상 snapshot”은 status가 `approved`(운영 사용 승인됨)이고 보존기간 내인 snapshot으로 한정한다. `generated`는 빌드 완료/고정 상태지만 운영 승인 전(비서빙)이므로 사용자 노출/폴백 기준에서 제외한다.
- 마지막 정상 snapshot = 위 조건을 만족하는 `approved` snapshot 중 `source_cutoff_at`가 가장 최근인 것.
- 미승인 `generated` snapshot은 사용자 freshness/기준 데이터로 노출하지 않는다(짝 문서 [사용자 / 어드민 API 기획](user_admin_api_plan_20260625.md) 2.6, [MySQL 적재 기획](periodic_raw_collection_mysql_plan_20260623.md) `artwork_snapshot.status` 정의와 일치).

폴백 케이스:

| 상황 | 화면 처리 |
|---|---|
| 예측 서버/모델 응답 불가 | 가격 카드/예측 결과를 비노출하고 “일시적으로 가격을 제공할 수 없음” 안내 |
| snapshot 신선도 SLA(10일) 이내 | 정상 노출. 데이터 기준일(as_of)만 표기하고 신선도 경고는 표시하지 않음 |
| snapshot 신선도 10일 초과 ~ 21일(운영 파라미터 §E `FRESH-HIDE-M`, M>N) 이내 | 마지막 정상 snapshot 기준 값(구데이터)을 제공하되 데이터 기준일(as_of)과 신선도 경고를 함께 노출 |
| snapshot 신선도 21일 초과 | 가격 카드/예측 결과 자체를 숨김(구데이터 무한 노출 금지). “현재 기준 데이터로 가격을 제공할 수 없음” 안내 |

단계적 처리 기준:

- SLA 10일 이내 = 정상 노출.
- 10일 초과 ~ 21일(M>N) = 구데이터 + 신선도 경고 표기.
- 21일 초과 = 카드 자체 숨김. 오래된 값을 무한정 보여주지 않는다.

데이터 freshness와 모델/deployment freshness 불일치:

- 사용자에게 보이는 as_of는 “현재 active deployment가 학습에 사용한 snapshot의 `source_cutoff_at`”이다(최신 수집 snapshot이 아니라, 운영 중인 모델이 실제로 학습에 쓴 snapshot 기준).
- 그 snapshot과 최신 정상 snapshot의 괴리가 임계 14일(운영 파라미터 §E `FRESH-MODEL-GAP`)을 넘으면, 데이터는 새로 들어왔지만 모델이 아직 반영하지 못한 상태이므로 신선도 경고를 표시한다.
- 즉 데이터 freshness(최신 snapshot)와 모델/deployment freshness(active deployment가 학습에 쓴 snapshot)가 어긋날 때는, 사용자에게 보이는 as_of를 deployment 기준으로 고정하고 괴리가 14일을 넘으면 경고로 처리한다.

표시 원칙:

- 장애 상황에서도 원천 사이트명/원천 URL은 노출하지 않는다.
- 구데이터를 보여줄 때는 “이 값은 10일 이전 기준”임을 사용자가 알 수 있게 한다.
- “가격을 계산할 수 없음(장애)”과 “계산은 되었으나 데이터가 오래됨(신선도 경고)”을 다른 상태로 보여준다.

## 3. 어드민 검수 흐름

```text
[수집 완료]
        |
        v
[검수 큐 생성]
  - 이름 alias 큐
  - 동명이인 큐
  - artist identity 큐
  - 신규 작가 후보 큐
  - 작품 품질 검수 큐
        |
        v
[운영자 검수]
  - 승인
  - 반려
  - 보류
  - 수정 후 승인
        |
        v
[snapshot 반영 판단]
  - 반영 가능 row
  - 보류 row
  - 제외 row
```

검수 큐별 처리:

| 큐 | 들어오는 조건 | 검수 조치(주체) | 결과 |
|---|---|---|---|
| 이름 alias 큐 | 한글/영문 표시명 후보가 자동 확정되지 않음 | 표시명 승인/수정/반려(운영자) | 승인 alias는 작가 매칭 후보로 사용 |
| 동명이인 큐 | 같은 alias가 여러 기존 artist_key 후보에 걸림 | 올바른 후보 선택 또는 반려(운영자) | 잘못된 후보 연결 금지 |
| artist identity 큐 | 기존 artist_key 연결 후보가 있으나 자동 확정 조건 미달 | 연결 검토/보류/반려(운영자), 기존 키 연결 확정(데이터 관리자) | 확정 시 기존 artist_key에 연결 |
| 신규 작가 후보 큐 | 연결 가능한 기존 artist_key 후보가 없음 | 보류/반려(운영자), 신규 artist_key 생성 승인(데이터 관리자) | 승인 시 최종 artist_key 생성 |
| 작품 품질 검수 큐 | 가격/크기/재료/상태 파싱 문제 | 수정/보류/제외 | snapshot 반영 여부 결정 |

> 권한 주: 검수 큐의 보류/반려/수정 등 상태 변경은 운영 담당자가 수행하지만, 최종 `artist_key` 생성(신규 생성·기존 키 연결 확정)과 snapshot 생성 승인은 데이터 관리자 권한이다. 운영 초기에는 슈퍼유저가 운영 담당자/데이터 관리자 권한을 모두 가진 어드민으로 처리할 수 있다. 상세 권한 기준은 [사용자 / 어드민 화면 구조 및 기능 기획](user_admin_screen_structure_plan_20260625.md) 5장과 [사용자 / 어드민 API 기획](user_admin_api_plan_20260625.md) 2.2를 따른다.

> 역할 명칭 주: 이 문서에서 “운영자”는 운영 문서([주기 수집 운영 문서](weekly_crawler_mysql_operation_plan_20260624.md) 11장)의 4역할(개발자 / 운영 담당자 / 데이터 분석가 / 데이터 관리자) 중 **운영 담당자**를 가리킨다. run 사용 가능 여부와 검수 큐 처리는 운영 담당자, 학습 피처 승격 판단은 데이터 분석가, 최종 `artist_key`·snapshot 승인은 데이터 관리자가 맡는다.

검수 큐 명칭 매핑(운영 개념 큐 ↔ 물리 큐/API):

| 운영 개념 큐(시나리오/운영 문서 표현) | 물리 큐(어드민) | API |
|---|---|---|
| 이름 alias 큐 / 한글명 검수 큐 | 작가명 검수 큐 | `GET /api/v1/admin/review/artist-names` |
| 동명이인 큐 / artist identity 큐 | artist_key 연결 검수 큐 | `GET /api/v1/admin/review/artist-identities` |
| 신규 작가 후보 큐 | 신규 작가 후보 큐 | `GET /api/v1/admin/review/new-artists` |
| 작품 품질 검수 큐 | 작품 품질 검수 큐 | `GET /api/v1/admin/review/artworks` |

> 매핑 기준: 한글 복원/음역 검수와 표시명/alias 검수는 별도 물리 큐가 아니라 `작가명 검수 큐`의 탭/필터로 운영한다. `동명이인 큐`와 `artist identity 큐`는 단일 `artist_key 연결 검수 큐`로 합쳐진다. 단일 기준은 [artist_key 및 작가명 표준화 흐름](artist_key_standardization_flow_20260624.md) 7장의 큐 명칭 매핑 주석이다.

어드민 화면 필수 표시:

- 원천 사이트
- 원천 URL
- 원천 작가 ID/slug
- 원천 작가명
- 한글/영문 표시 후보
- 후보 artist_key 목록
- 생년, 국적, 활동지
- 작품 수, 가격대, 대표 작품
- 자동 확정 근거
- 검수 필요 사유
- 충돌 사유
- 승인/반려/보류 버튼
- 승인자, 승인시각, 승인메모

### 3.1 어드민 시나리오: 수집 결과 확인

조건:

- 주기 수집이 완료되었거나 부분 실패했다.

흐름:

```text
수집 run 목록 확인
  -> 사이트별 성공/실패 요약 확인
  -> 실패 또는 검수 필요 건수 확인
  -> 상세 run으로 이동
```

운영자가 판단해야 하는 것:

- 이번 수집 결과를 snapshot 후보로 넘겨도 되는가?
- 특정 사이트만 재수집해야 하는가?
- parser 수정이 필요한 구조 변경인가?
- 실패가 일시적인 네트워크 문제인지, 사이트 구조 변경인지 확인이 필요한가?

### 3.2 어드민 시나리오: 작품 품질 검수

조건:

- 가격, 크기, 재료/지지체, 작품 유형, 중복 여부 중 하나 이상이 자동 확정되지 않았다.

흐름:

```text
작품 품질 검수 큐 진입
  -> 원천값과 표준화 후보값 비교
  -> 수정 / 보류 / 제외 / 승인 선택
  -> 사유 기록
```

운영자 조치:

| 조치 | 의미 | 다음 상태 |
|---|---|---|
| 승인 | 표준화 후보값을 그대로 사용 | snapshot 반영 후보 |
| 수정 후 승인 | 운영자가 값을 고친 뒤 사용 | snapshot 반영 후보 |
| 보류 | 판단 근거가 부족함 | 검수 대기 유지 |
| 제외 | 학습/운영에 쓰면 안 됨 | 제외 row |

### 3.3 어드민 시나리오: 작가명 한글화/영문화 검수

조건:

- 원천 작가명만 있고 서비스 표시용 한글명 또는 영문명 후보가 확정되지 않았다.
- 자동 변환값이 원천값과 충돌하거나 신뢰도가 낮다.

흐름:

```text
작가명 검수 큐 진입
  -> 원천 작가명 확인
  -> 자동 변환 후보 확인
  -> 서비스 표시명 승인 또는 수정
  -> alias 후보 생성/승인
```

처리 원칙:

- 원천값은 수정하지 않는다.
- 서비스 표시용 이름은 별도 컬럼으로 관리한다.
- 자동 변환값과 사람이 승인한 값을 구분한다.

### 3.4 어드민 시나리오: 기존 artist_key 연결 검수

조건:

- 기존 `artist_key` 후보가 있으나 자동 확정 기준을 통과하지 못했다.

흐름:

```text
artist identity 후보 확인
  -> 후보별 생년/국적/활동지/대표 작품/원천 URL 확인
  -> 운영자 연결 검토/보류/반려
  -> 데이터 관리자 연결 확정 승인
  -> 승인자와 승인시각 기록
```

처리:

- 운영자 검토 후 데이터 관리자가 승인하면 해당 원천 작가 row가 기존 `artist_key`에 연결된다.
- 반려하면 해당 후보와의 연결을 금지하고, 다른 후보 또는 신규 작가 후보로 이동한다.
- 보류하면 운영자 검수 큐에 남긴다.

### 3.5 어드민 시나리오: 신규 artist_key 생성 승인

조건:

- 연결 가능한 기존 `artist_key` 후보가 없다.
- 신규 작가 후보로 들어왔다.

흐름:

```text
신규 작가 후보 확인
  -> 원천 작가 ID/URL/작가명/작품 목록 확인
  -> 기존 작가 중 누락 후보가 없는지 확인
  -> 신규 artist_key 생성 승인 또는 보류/반려
```

처리:

- 승인 전에는 최종 `artist_key`를 만들지 않는다.
- 승인하면 신규 `artist_key`를 생성하고 승인자, 승인시각, 승인 사유를 남긴다.
- 반려하면 해당 후보는 확정 작가로 쓰지 않는다.

### 3.6 어드민 시나리오: snapshot 생성 승인(데이터 관리자)

조건:

- 수집, 표준화, 작가 검수, 작품 품질 검수가 끝났다.

흐름:

```text
snapshot 후보 확인
  -> 반영 가능 row 수 확인
  -> 보류/제외 row 수 확인
  -> 주요 품질 지표 확인
  -> 데이터 분석가 학습 피처 승격 판단
  -> snapshot 생성 승인
```

데이터 관리자가 확인할 항목(운영 담당자 검수 완료 후):

- 직전 snapshot 대비 신규/변경/삭제 후보 수
- 가격 보유율
- 크기 파싱 성공률
- 작가 확정률
- 제외 사유 상위 항목
- 사이트별 데이터 편중

데이터 분석가 단계(snapshot 승인 직전):

- 결측률, 가격/크기/재료 분포, 원천별 편향, unmapped 목록을 보고 이번 후보를 **학습 피처로 승격할 수 있는지** 판단한다.
- 보존만 하고 아직 모델 피처로 쓰지 않는 지표(인기도/전시량 등)는 승격 대상에서 분리한다.
- 학습 피처 승격 판단 결과는 데이터 관리자의 snapshot 생성 승인 입력으로 넘긴다. 권한 경계는 [주기 수집 운영 문서](weekly_crawler_mysql_operation_plan_20260624.md) 11장을 따른다.

### 3.7 어드민 시나리오: snapshot 승인에서 서빙 반영까지

조건:

- snapshot 생성이 승인되어 새 학습 snapshot이 만들어졌다.

흐름:

```text
snapshot 생성 승인
  -> (별도 단계) 모델 학습
  -> (별도 단계) 모델 검증
  -> price_model_deployment의 active row 교체(승격)
  -> 사용자 예측에 반영
```

처리 원칙:

- snapshot 승인은 곧바로 사용자 예측에 반영되지 않는다. 수집 snapshot 생성, 모델 학습, 모델 운영 승격은 서로 다른 단계다.
- 새 snapshot이 사용자에게 보이려면, 그 snapshot으로 학습·검증한 모델을 `price_model_deployment`의 해당 route active row로 교체(승격)해야 한다. route별 active deployment는 하나만 허용한다.
- 따라서 snapshot이 갱신된 시점과 사용자가 체감하는 시점 사이에는 정상적인 시차가 있다. 운영자는 “snapshot은 승인됐는데 예측 값이 안 바뀐다”를 장애로 오인하지 않는다. 사용자 예측이 어느 모델·배포를 쓰는지는 예측 응답의 `model_version`/`deployment_id`(2장 `price_prediction_log` 적재)로 확인한다.

## 4. 수집 운영 시나리오

### 4.1 정상 수집

조건:

- 4개 사이트 crawler가 정상 종료된다.
- 목록 수집과 상세 수집이 기준 성공률을 통과한다.
- raw 저장, staging 생성, 표준화, 품질 점검이 모두 완료된다.

흐름:

```text
cron 시작
  -> collector_run 생성
  -> 사이트별 목록 수집
  -> 상세 수집
  -> raw 저장
  -> interpreted/normalized staging 생성
  -> artist 후보/검수 큐 생성
  -> 품질 점검
  -> snapshot 후보 생성
  -> run summary 생성
  -> 운영자에게 성공 요약 표시
```

운영자에게 보여줄 요약:

- 사이트별 수집 작품 수
- 신규 작품 수
- 사라진 작품 수
- 가격 변경 작품 수
- 상세 수집 실패 수
- 가격 보유율
- 크기 파싱 성공률
- 검수 큐 신규 유입 수
- snapshot 반영 가능 row 수

### 4.2 부분 실패

부분 실패 예:

- 특정 사이트만 실패
- 목록은 성공했지만 일부 상세 페이지 실패
- HTTP 성공이나 파싱 실패
- 작가 정보만 누락
- 가격/크기 파싱만 실패

처리 원칙:

- 성공한 사이트의 raw는 저장한다.
- 실패한 사이트나 실패 URL은 `collector_run`과 `raw_fetch`에 실패 사유를 남긴다.
- 실패한 사이트의 신규 데이터는 해당 주 snapshot에 자동 반영하지 않는다.
- 마지막 정상 snapshot은 유지한다.
- 운영자에게 실패 요약을 보여준다.

운영자 알림 요약:

| 항목 | 표시 내용 |
|---|---|
| 실패 범위 | 사이트 전체 실패인지, 상세 일부 실패인지 |
| 실패 수 | 실패 URL 수, 실패 row 수 |
| 실패 사유 | HTTP 오류, timeout, parser 오류, 필수 필드 누락 |
| 영향 범위 | 이번 주 snapshot 반영 가능 여부 |
| 권장 조치 | 재시도, 보류, parser 수정 요청, 사이트 구조 변경 확인 |

### 4.3 품질 미달

품질 미달 예:

- 가격 숫자 없음
- 판매문의/가격문의/placeholder 가격
- 가로/세로 cm 없음
- 재료 분류 실패
- 입체/설치/영상/혼합매체 제외 후보
- 중복 후보
- 작가명 누락

처리:

- raw는 유지한다.
- 품질 플래그를 남긴다.
- 학습 snapshot에는 바로 넣지 않는다.
- 운영자 검수 또는 제외 판단을 기다린다.

상태:

| 상태 | 의미 |
|---|---|
| `ready_for_snapshot` | snapshot 반영 가능 |
| `needs_review` | 운영자 검수 필요 |
| `excluded` | 학습/운영 snapshot 제외 |
| `processing_failed` | 수집 또는 파싱 실패로 다음 단계 진행 불가 |

`processing_failed`는 데이터 자체를 삭제한다는 뜻이 아니다. 해당 수집 run 또는 row가 다음 처리 단계로 넘어가지 못한다는 운영 상태다.

이 표의 상태값은 운영 개념 상태이며 물리 컬럼 enum이 아니다. enum 단일 기준은 [MySQL 적재 기획](periodic_raw_collection_mysql_plan_20260623.md) 5.0.2이며, 실제 저장은 다음과 같이 매핑한다.

- `ready_for_snapshot`: 필수·검수 조건을 통과한 row. snapshot 생성 시 `artwork_snapshot_item.include_status=included`로 고정된다.
- `needs_review`: 각 검수 테이블의 `review_status` 또는 `normalized_*_staging.artist_identity_status`.
- `excluded`: `artwork_snapshot_item.include_status=excluded`(+`exclude_reason`).
- `processing_failed`: `collector_run.status=failed` 또는 staging의 `quality_flags_json` 처리 실패 플래그.

## 5. artist_key 시나리오

### 5.1 기존 artist_key 연결

조건:

- 같은 `source + artist_source_id`가 이미 확정된 `artist_key`에 연결되어 있다.

처리:

- 점수 계산 없이 기존 `artist_key`에 연결한다.
- 운영자 검수 큐로 보내지 않는다.

### 5.2 cross-source 자동 확정

조건:

- `alias_exact` 또는 `alias_approved`가 있다.
- 서로 다른 원천 후보 양쪽 모두 `birth_year_confidence=high`인 생년이 있다.
- 생년이 같다.
- 같은 alias가 2개 이상의 artist_key 후보에 걸리지 않는다.
- 강한 충돌 조건이 없다.

처리:

- 기존 `artist_key`에 자동 연결한다.
- `review_status=auto_approved`로 기록한다.
- 자동 확정 시각과 규칙 버전을 남긴다.
- 자동 확정 결과는 샘플 검수 대상에 포함한다.

### 5.3 수동 검수

조건:

- alias는 맞지만 고신뢰 생년이 없다.
- fuzzy alias만 있다.
- 같은 alias가 여러 후보에 걸린다.
- 국적/활동지/작품군/가격대가 충돌 경고를 만든다.

처리:

- `artist_key`에 바로 연결하지 않는다.
- 운영자 검수 큐로 보낸다.
- 운영자가 검수 큐에서 기존 artist_key 연결/신규 생성 제안 또는 보류·반려를 처리하고, 기존 연결 확정·신규 artist_key 생성은 데이터 관리자가 승인한다.

### 5.4 신규 작가 후보

조건:

- 연결 가능한 기존 `artist_key` 후보가 없다.
- 원천 작가명과 원천 작가 URL 또는 `source_artist_raw_id`가 있다.
- 작품 row 연결 정보가 있다.

처리:

- 신규 작가 후보 큐로 보낸다.
- 이 단계에서는 `artist_key`를 발급하지 않는다.
- 운영자 검수 후 데이터 관리자가 승인한 뒤에만 최종 `artist_key`를 생성한다.

## 6. snapshot 반영 시나리오

학습 snapshot에 들어갈 수 있는 row:

- 가격 숫자가 있다.
- 통화가 있다.
- 가로/세로 cm가 있다.
- 입체/설치/영상/혼합매체 제외 조건에 걸리지 않는다.
- 중복 제거 기준을 통과한다.
- 작가 정보가 확정되었거나, 해당 모델 경로에서 작가 확정 없이 사용할 수 있는 입력으로 분류된다.

보류 row:

- 가격/크기/재료/상태 검수 필요
- artist_key 검수 필요
- 동명이인 후보
- 신규 작가 후보 승인 대기
- 수집 실패 사이트의 신규 row

제외 row:

- 가격 없음 또는 가격문의
- placeholder 가격
- 명백한 입체/설치/영상/혼합매체 제외 대상
- 필수 크기 누락
- 중복으로 판단된 row

point-in-time 규칙:

- snapshot은 `source_cutoff_at` 이전 수집분만 포함한다(point-in-time). cutoff 이후 수집/변경분은 해당 snapshot에 섞이지 않고 다음 snapshot으로 넘어간다. 이 값이 사용자 화면의 데이터 기준일(as_of)이 된다. 컬럼·환산 단일 기준은 [MySQL 적재 기획](periodic_raw_collection_mysql_plan_20260623.md)을 따른다.

## 7. 시나리오 검토 기준

이 시나리오 문서는 아래 질문에 답할 수 있어야 한다.

- 수집이 성공하면 운영자는 무엇을 확인하는가?
- 일부 실패하면 어떤 데이터가 보류되는가?
- 어떤 row가 검수 큐로 가는가?
- 신규 작가는 언제 `artist_key`가 생기는가?
- 어떤 row가 학습 snapshot에 들어가는가?
- 사용자는 어떤 상황에서 예측 결과, 보완 안내, 검수 필요 안내를 보게 되는가?
