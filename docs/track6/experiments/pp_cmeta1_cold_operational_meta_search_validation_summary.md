# PP-CMETA1 Cold 운영형 작가 메타/검색 피처 검증 요약

- 실행일: 2026-06-18
- 실험 폴더: `experiments/track6/PP-CMETA1_cold_operational_meta_search_validation`
- 목적: 같은 작가 가격 이력 없이, 작품 정보와 운영에서 수집 가능한 작가 메타/인터넷 검색 피처만으로 Cold 가격 예측이 가능한지 확인

## 1. 확인하려는 구조

사용자가 기대한 Cold 구조는 아래와 같다.

1. 가격이 있는 과거 작품에서 작품 정보와 작가 메타/검색 피처의 관계를 학습한다.
2. 신규 작가는 같은 작가의 과거 가격 이력이 없으므로 작가 가격 통계는 쓰지 않는다.
3. 대신 신규 작가의 생년, 활동량, 팔로워, 전시/갤러리, 검색 문맥 같은 정보를 인터넷/캐시에서 수집한다.
4. 수집한 작가 외부 정보와 작품 크기/매체/지지체 정보를 조합해 가격을 예측한다.

이번 실험은 이 구조에 맞추기 위해 아래 항목을 제외했다.

- `artist_key`를 모델 피처로 사용하지 않음
- 같은 작가 가격 중앙값, 같은 작가 작품 수, 같은 작가 면적단가 같은 가격 이력 피처를 사용하지 않음
- 작가별 `search_delta_lookup` 후처리를 사용하지 않음

## 2. 후보 비교

## 3. 해석

운영형 Cold 방향은 실험 근거가 있다.

작품 정보만 쓰는 후보보다 작가 메타/검색/전시 피처를 함께 쓴 후보가 test MdAPE, MAPE, p95 APE 모두 개선됐다. 따라서 “학습 작가들의 메타/검색 패턴을 배워 신규 작가의 외부 정보와 작품 정보로 가격을 예측한다”는 접근은 성능 근거가 있다.

다만 현재 최고 성능 Cold v0.3의 `0.409820 / 0.849260 / 2.346465`에는 아직 못 미친다. v0.3은 작가별 `search_delta_lookup` 후처리까지 포함하므로, 이번 실험의 순수 운영형 모델과 직접 같은 의미로 비교하면 안 된다. 이번 실험은 lookup 없이 raw/cached feature만으로 작동 가능한 모델 방향을 검증한 것이다.

## 4. 운영 적용 설계

운영에 적용하려면 아래 순서가 필요하다.

1. 입력 작가명을 정규화한다.
2. 작가 registry에서 기존 작가인지 확인한다.
3. Warm/Warm-lite에 필요한 같은 작가 가격 이력이 없으면 Cold로 보낸다.
4. Cold에서는 작품 크기/매체/지지체 피처를 생성한다.
5. 작가 메타 cache에서 생년, 국적, 팔로워, 전체 작품 수 등 비가격성 메타를 조회한다.
6. 메타가 부족하면 인터넷 검색 수집을 실행하거나, 승인된 검색 cache를 조회한다.
7. 검색 결과에서 미술 문맥 수, 전시 문맥 수, 갤러리 문맥 수, 동명이인 위험, 검색 품질 점수를 만든다.
8. 전시/갤러리 구조화 피처가 있으면 함께 넣고, 없으면 missing flag로 모델에 전달한다.
9. LightGBM Quantile q10/q50/q90 모델로 대표 가격과 가격 범위를 예측한다.
10. 예측 폭이 넓거나 검색 품질이 낮으면 낮은 신뢰도와 검수 필요 표시를 함께 반환한다.

## 5. 남은 조건

이번 실행은 기존 동결 검색 cache를 사용했다. 따라서 운영 승격 전에는 아래가 추가로 필요하다.

- 신규 작가 live search 수집 또는 승인 cache 생성
- 검색 결과 URL dedup, 동명이인 방어, 수집 실패 fallback
- live search 피처와 학습 피처의 분포 차이 점검
- search cache가 없는 작가에서 성능이 얼마나 떨어지는지 별도 검증
- 최종 API에서 `artist_key` lookup 보정 없이 동일 schema로 예측 가능한지 parity 검증

## 6. 결론

사용자가 기대한 Cold 방식의 핵심 실험은 이번 PP-CMETA1로 별도 검증했다.

결론은 “가능성 있음”이다. 작품 정보만 쓰는 Cold보다 작가 메타/검색/전시 피처를 함께 쓰는 운영형 Cold가 명확히 개선된다. 다만 현재 최고 성능 v0.3보다 낮으므로 바로 최종 운영 모델로 교체하기보다는, live search 수집 파이프라인과 fallback 검증을 완료한 뒤 v0.3 lookup 의존도를 줄이는 차기 Cold 후보로 관리하는 것이 맞다.
