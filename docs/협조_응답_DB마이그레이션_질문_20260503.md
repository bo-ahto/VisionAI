## 1. 우선순위 재조정 (코덱스 review 반영)

협조_필요사항_정리 §2.1 (`career_stage` INT → REAL) 의 긴급도가 처음 plan 보다 **낮음** 으로 평가됐습니다. 이유:

- 서빙 경로의 predictor 가 DB 의 `career_stage` 값을 **직접 사용 안 함**
- 대신 `birth_year / solo_count / group_count / fair_count / followers` 로 v2 점수 재계산
  (`primary_feature_builder.py:198`)
- 따라서 INT 1~4 → REAL 0~8 매핑 자체보다, **다음 사항이 더 중요**:

### 새 우선순위

| # | 항목 | 우선순위 (코덱스) | 이유 |
|---|------|---|---|
| 3.A | **`training_count` source-of-truth 일원화** | **P1 (가장 위험)** | warm artist routing 은 JSON 권위, B 등급 판정/API 응답은 DB count 영향 — 둘 다 active 면 inconsistency |
| 3.B | `career_stage` 타입 INT → REAL (1.0~4.0 보존) | P2 | predictor 영향 낮음, v2 backfill 은 별도 job |
| 3.C | (선택) `gallery_name` 컬럼 / PredictRequest field | P2 | gallery_name 신호 회복 (별도 PR) |

## 2. 운영팀에 보내는 질문 (4건)

### Q1. 갤러리 판매 데이터 수신 예정일 = D-day anchor

- **목적**: 마이그레이션 완료가 데이터 수신 직전에 와야 함
- **요청**: 예정일 (또는 window 범위) 알려주세요
- **이유**: D-7 (SQL/backfill 준비) ~ D-3 (STAGING) ~ D-day (production) 의 anchor 결정

### Q2. 작가 DB 추가 일정 — 갤러리 판매 데이터와 동시 진입?

- 두 데이터가 **동시 진입** 이면 마이그레이션 1번
- **별개 일정** 이면 마이그레이션 2번 (career_stage 만 먼저 / training_count 별도)
- 우선순위 차이로 마이그레이션을 분할 가능 (3.A 만 먼저 / 3.B 는 나중)

### Q3. **`training_count` 가 어디서 채워지는가? (source-of-truth 결정용)**

이게 가장 중요한 질문입니다. 코덱스 분석:

```
현재 server 동작:
  - warm routing: warm_artist_slugs.json 권위 (JSON file 우회 — PR #20)
  - B 등급 판정: artist_matcher.py 가 DB.training_count 사용
  - API 응답 model_info.training_count: DB 값

→ 두 source 가 다른 row 를 가질 수 있음 (32명 미스라우팅 위험 — §2.2 명시)
```

**선택지**:
- **(a) DB 가 권위, JSON 우회 deprecate**: server 코드 변경 (warm routing 도 DB query) — 작업량 큼, race condition 위험
- **(b) JSON 이 권위, DB 는 derived**: 운영 측에서 정기적 sync (artifact build 시 dump) — 현재 상태 유지, 명시만
- **(c) 둘 다 유지 + version 컬럼**: `warm_artifact_version` 으로 어느 시점 sync 인지 명시 — middle ground

운영팀에서 어느 source 가 진실인지 확인 필요:
1. 운영팀 ETL 가 `artists.training_count` 를 어디서 (raw count? warm artifact?) 채우는지?
2. 정기적 sync 가 있는가? (예: nightly job)
3. `warm_artist_slugs.json` 의 update 주기 / 최신성?

### Q4. Down-time 허용 시간

- **5분 이내** (단일 transaction, 권장) — `ALTER TABLE` + 빠른 backfill 가능
- **10-30분** (분할 migration) — `ADD COLUMN nullable` → backfill batch → `ALTER COLUMN NOT NULL`
- **별도 maintenance window** (1-4h) — 안전한 검증 + rollback 여유

마이그레이션 항목 별 추정:

| 항목 | 추정 down-time | 안전 옵션 |
|---|---|---|
| 3.A `training_count` 동기화 | 0min (READ-only update) | 0 |
| 3.B `career_stage` REAL 변경 | 1-3min (ALTER COLUMN type) | nullable add → swap → drop |
| 3.C `gallery_name` 추가 | 0min (ADD COLUMN nullable) | 0 |

## 3. 권장 일정 (D-day 결정 후)

```
D-7   SQL + backfill + rollback script 준비
      writer update 스코프 정리 (모든 INSERT/UPDATE path)
D-5   STAGING / production replica 에서 rehearse — backfill idempotency 검증
D-3   STAGING 적용 + 1일 안정 모니터링
D-1   운영팀 + backend 양측 rollback plan 최종 sign-off
D-day production 적용 (down-time 허용 범위 안)
D+1   Q1-Q4 metric 모니터링 (warm routing / B 등급 정합 / API 응답 일관성)
D+3   warm JSON 우회 코드 deprecate PR (단, Q3.선택 결과에 따라)
```
